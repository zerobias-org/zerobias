# Module SDKs

Module SDKs are language-specific client libraries that provide type-safe,
IDE-friendly interfaces for consuming Module operations. They are
auto-generated from OpenAPI specifications and cover both **Hub Modules**
(integrations defined in [`module/`](https://github.com/zerobias-org/module))
and **Platform Services** (closed-source services like Hub Server, Dana,
etc.).

> 📦 **Installing SDK packages requires a `ZB_TOKEN`.**
> `@zerobias-org/sdk-*` and `@zerobias-com/*-sdk` are published to
> `https://pkg.zerobias.org/`. Once you have a token (see
> [`RegistrySetup.md`](RegistrySetup.md)), they install like any other
> npm package — `npm install @zerobias-org/sdk-amazon-aws-s3` just works.
>
> Source for the **Hub Module SDKs** lives inside the public
> [`module/`](https://github.com/zerobias-org/module) repo (each module's
> SDK is generated alongside the module itself), so you can read the code
> here in the meta-repo without a token. **Platform Service SDK source
> is private** — the SDKs are usable, but the underlying service repos
> are not part of this meta-repo.

> 🔄 **Scope migration in progress.** Module and SDK packages are moving
> from the legacy `@auditmation/*` scope to `@zerobias-org/*` (open-source
> content) and `@zerobias-com/*` (closed-source platform services). Older
> versions of some packages may still be published under `@auditmation/*`;
> new releases use the new scopes. The package pattern is the same in
> both — only the prefix changes.

---

## SDK vs Client vs Library

Terminology used across the codebase:

| Term | Meaning |
|------|---------|
| **SDK** (preferred) | Rich developer experience: types, inline docs, examples, typed errors, retries, pagination helpers |
| **Client** | Narrower — usually an HTTP wrapper with basic API access |
| **Library** | Too generic; avoid for API-access packages |

In docs and naming, prefer "SDK". `-api-client` suffix is acceptable in
package names where "SDK" doesn't fit grammatically.

---

## SDK types

There are two SDK shapes, distinguished by **how the call reaches the
target system**:

### 1. Hub Module SDKs — proxied execution

**What they do:** invoke a Hub Module operation (e.g. `listBuckets` on AWS
S3) by routing through the closed-source Hub Server, which in turn invokes
the deployed module on a Hub Node.

**Package pattern:** `@zerobias-org/sdk-<vendor>-<product>` (TypeScript)

Examples:

- `@zerobias-org/sdk-amazon-aws-s3`
- `@zerobias-org/sdk-microsoft-azure-ad`
- `@zerobias-org/sdk-github-github`

```typescript
import { S3Client } from '@zerobias-org/sdk-amazon-aws-s3';
import { HubClient } from '@zerobias-com/hub-sdk';

const hub = new HubClient({
  baseUrl: 'https://hub.zerobias.com',
  apiKey: process.env.HUB_API_KEY,
});

// Routed through Hub Server → Hub Node → module
const s3 = new S3Client(hub, { connectionId: 'conn-prod-s3' });
const buckets = await s3.listBuckets();
```

### 2. Platform Service SDKs — direct execution

**What they do:** call a closed-source Platform Service's REST API
directly (Hub Server, Dana, fileservice, etc.). No Hub Node hop.

**Package pattern:** `@zerobias-com/<service>-sdk` (TypeScript)

Examples:

- `@zerobias-com/hub-sdk` — Hub Server API
- `@zerobias-com/dana-sdk` — authentication
- `@zerobias-com/platform-sdk` — core platform
- `@zerobias-com/fileservice-sdk` — file storage

```typescript
import { HubClient } from '@zerobias-com/hub-sdk';

const hub = new HubClient({
  baseUrl: 'https://hub.zerobias.com',
  apiKey: process.env.HUB_API_KEY,
});

const nodes = await hub.nodes.list();
const deployment = await hub.deployments.create({
  nodeId: nodes.items[0].id,
  moduleId: '@zerobias-org/module-amazon-aws-s3',
  version: '1.2.3',
});
```

> The Platform Services themselves are closed source and live in a
> private organization. The **SDKs** that talk to them are what's
> documented here.

### Aggregation SDK: `zb-client`

`zb-client` is an aggregation package that bundles multiple module and
service SDKs behind a single, higher-level interface. It's installable
with `ZB_TOKEN` like any other published package, but its **source repo
is private** and not part of this meta-repo. Reach for it when you want
to consume several SDKs together without wiring each one up by hand.

## How SDKs are generated

SDKs are **auto-generated from OpenAPI specs** — the `api.yml` next to
each module or service is the single source of truth. The generation
pipeline differs slightly between the two SDK kinds.

### Hub Module SDKs — generated by gradle/zbb

For each module sub-package in [`module/`](https://github.com/zerobias-org/module),
the Gradle build (`zbb` plugin from
[`util`](https://github.com/zerobias-org/util)) produces a `hub-sdk/`
directory containing the generated TypeScript SDK. That directory is
what gets published as `@zerobias-org/sdk-<vendor>-<product>`.

```
module/package/<vendor>/<product>/<api-type>/
├── api.yml                  # OpenAPI spec (source of truth)
├── connectionProfile.yml
├── connectionState.yml
├── src/                     # module implementation
├── test/
└── hub-sdk/                 # ← generated by gradle (zbb)
    ├── src/
    │   ├── api/             # generated API classes
    │   └── model/           # generated models
    └── package.json         # published as @zerobias-org/sdk-<vendor>-<product>
```

Run `./gradlew :<module>:gate` to validate; the SDK is regenerated as
part of the build, so don't hand-edit anything in `hub-sdk/`.

### Platform Service SDKs — generated from OpenAPI in their own repos

Platform Services maintain their `api.yml` in their (closed-source)
service repos. The generated `api-client/` package next to the spec is
published as `@zerobias-com/<service>-sdk`. The generation tooling
itself (`@zerobias-com/util/codegen`) lives in the public
[`util`](https://github.com/zerobias-org/util) repo, even though the
specs it consumes don't.

## Execution architecture

### Hub Module SDK (proxied)

```
Application code
    ↓ s3.listBuckets()
Hub Module SDK (@zerobias-org/sdk-amazon-aws-s3)
    ↓ REST invoke
Hub Server (closed source)
    ↓ WebSocket invocation
Hub Node
    ↓ in-process call
Module implementation (@zerobias-org/module-amazon-aws-s3)
    ↓ AWS API call
AWS S3
```

The SDK's job: translate method calls into Hub Server invocations, route
to the right `connectionId` / `deploymentId`, decode typed responses and
errors.

### Platform Service SDK (direct)

```
Application code
    ↓ hub.nodes.list()
Platform Service SDK (@zerobias-com/hub-sdk)
    ↓ HTTP REST request
Dana API Gateway (JWT validation, closed source)
    ↓ authenticated request
Platform Service (Hub Server, etc.)
    ↓
Database / external systems
```

The SDK's job: HTTP client config (base URL, auth, timeouts), request
serialization, response/error mapping, retries.

## Direct vs proxied execution from the application's perspective

Hub Modules can be consumed two ways, and the **same SDK surface** is
available in both:

### Direct (in-process) — when you control credentials

```typescript
import { S3Producer } from '@zerobias-org/module-amazon-aws-s3';

const s3 = new S3Producer();
await s3.connect({
  accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
  secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
  region: 'us-east-1',
});

const buckets = await s3.listBuckets();
```

Use for CI/CD jobs, server-side tools, local development — anywhere you
can hold the target credentials yourself.

### Proxied (via Hub Server) — when you don't

```typescript
import { S3Client } from '@zerobias-org/sdk-amazon-aws-s3';
import { HubClient } from '@zerobias-com/hub-sdk';

const hub = new HubClient({ baseUrl: '...', apiKey: '...' });
const s3 = new S3Client(hub, { connectionId: 'conn-prod-s3' });

const buckets = await s3.listBuckets();  // identical method
```

Use from browsers, behind-firewall targets, or when credentials must be
managed centrally with RBAC / audit.

Applications can switch modes via config without changing call sites.

## TypeScript SDK features

TypeScript is the primary language; all SDKs ship with:

**Full type inference** — return types, enum types, paged result wrappers
all inferred end-to-end.

**Compile-time validation** of parameters:

```typescript
await hub.deployments.create({
  nodeId: 'node-123',
  // Error: Property 'moduleId' is missing
});
```

**Inline JSDoc** on every operation — autocomplete and tooltip docs
inside the IDE.

**Typed errors** mapped from HTTP status codes:

```typescript
import {
  UnauthorizedError, ForbiddenError, NotFoundError, ValidationError,
} from '@zerobias-com/hub-sdk';

try {
  await hub.nodes.get('missing-id');
} catch (err) {
  if (err instanceof NotFoundError) { /* ... */ }
}
```

**Pagination helpers** for paged list endpoints:

```typescript
let page = 1, hasMore = true;
while (hasMore) {
  const result = await hub.nodes.list({ pageSize: 100, pageNumber: page });
  processNodes(result.items);
  hasMore = result.hasNextPage;
  page++;
}
```

**Configurable HTTP layer** — timeouts, retries, custom logger,
token-provider callback:

```typescript
const hub = new HubClient({
  baseUrl: 'https://hub.zerobias.com',
  getToken: async () => await getJWT(),
  timeout: 30_000,
  maxRetries: 3,
});
```

| Language | Status | Notes |
|----------|--------|-------|
| TypeScript / JavaScript | ✅ Shipping | Browser + Node, primary target |
| Java | 🚧 Planned | Maven / Gradle, builder-pattern config |
| Python | 📋 Future | Type hints, PyPI |
| Go | 📋 Future | Context-based, Go modules |
| Rust / C# / Ruby | 📋 Community | Open to contributions |

All languages will share OpenAPI specs as the source of truth, so feature
parity is a code-generation concern, not a documentation one.

## Browser compatibility

| SDK kind | Browser? |
|----------|----------|
| Hub Module SDK (proxied) | ✅ Always — HTTP-only, CORS handled by Hub Server |
| Platform Service SDK | ✅ Yes — HTTP REST, JWT auth, CORS supported |
| Direct module import | ⚠️ Depends on the module — many use Node-only APIs (`fs`, `child_process`) and won't bundle for browsers |

For browser apps, **proxied execution is the default path** — direct
module import is for backends.

## Best practices

**Using SDKs:**

1. Never hardcode credentials — environment variables or a secret store.
2. Always catch typed errors; don't catch raw `Error`.
3. Handle pagination explicitly on listing endpoints.
4. Configure retries for transient failures (429, 503, network).
5. Use the SDK's logger hook for debugging — don't `console.log` inside
   the SDK.

**Authoring / extending SDKs (for module / service maintainers):**

1. **OpenAPI first.** Edit `api.yml`, regenerate — don't hand-edit the
   generated client.
2. Add `description` to every operation and parameter; the SDK's IDE docs
   come from there.
3. Add `example` values in the spec — they become docstring examples.
4. Follow semver strictly — SDK major version aligns with module/service
   major version.
5. Test generated SDKs against the live service (contract + integration
   tests), not just unit tests.

---

## Versioning

- **SDK version follows the underlying module/service version.**
  `module@1.2.3` → `sdk@1.2.3`.
- Breaking changes in the spec → major bump in the SDK.
- New operations → minor bump.
- Deprecations: marked `@deprecated` in JSDoc → TypeScript warning →
  runtime warning → removed in next major (6-month notice).

## Extending an SDK

Don't edit generated code. Wrap it instead:

```typescript
import { S3Client } from '@zerobias-org/sdk-amazon-aws-s3';

export class S3Helper extends S3Client {
  async findBucketByPrefix(prefix: string) {
    const buckets = await this.listBuckets();
    return buckets.find(b => b.name.startsWith(prefix));
  }
}
```

Same pattern works for caching, rate limiting (`p-retry`, `p-queue`), or
request batching.
